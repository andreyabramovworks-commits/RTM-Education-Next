# Отдельный поток проектирования внешнего вида

**Назначение:** подготовить визуальную систему RTM-Education-Next в отдельном чате и передать разработке проверяемый пакет решений. Этот документ не утверждает конкретную палитру, шрифт или библиотеку до визуального согласования.

## Почему отдельный чат

Визуальная работа требует сравнительных референсов, макетов, вариантов плотности, снимков состояний и нескольких циклов критики. Она не должна смешивать продуктовые решения и реализацию backend. Результаты визуального чата становятся приложением к спецификации после явного согласования пользователя.

## Рекомендуемый набор навыков

Все перечисленные навыки уже доступны локально; повторно скачивать их сейчас не требуется.

| Роль | Навык | Как использовать |
|---|---|---|
| Основной процесс | `development-workbench-skill` | Связать дизайн с реальными ролями, состояниями, API и критериями приёмки. |
| Визуальное направление | `design-taste-frontend` | Извлечь композицию, типографику, ритм и характер. Для RTM использовать как источник принципов, не копировать правила маркетингового лендинга в плотную админку. |
| Компоненты | `ready-solutions-skill` | Подобрать таблицу, формы, dialog, command palette, tree/select, DnD и редактор; проверить лицензию, зависимости и доступность. |
| Ресурсы и визуальная проверка | `web-creator` | Искать совместимые дизайн-системы и паттерны, проверять реальный браузер. Не превращать рабочее приложение в промо-сайт. |
| Анти-шаблонные правила | `no-ai-design-slop` | До макетов сформулировать, какие декоративные и шаблонные приёмы запрещены без функции. |
| Независимый аудит | `audit-ai-design-slop` | После макетов и после реализации удалить повторяющиеся оболочки, бессмысленные эффекты и ложную визуальную иерархию. |
| Критика и полировка | `impeccable` | Последовательно применить clarify, arrange, typeset, colorize, harden, normalize и audit/polish. |
| UI-тексты и типографика | `website-copy-typography` | Согласовать названия действий, ошибки, пустые состояния, иерархию текста и плотность русскоязычного интерфейса. |
| Проверка браузером | `playwright` | Проверить реальные маршруты, состояния, клавиатуру, desktop и мобильную пользовательскую часть. |

Если нужны редактируемые макеты, дополнительно использовать установленный Figma-плагин: `figma:figma-create-new-file` для отдельного файла, `figma:figma-generate-design` для экранов, `figma:figma-spec` для передачи токенов и компонентов. Начинать Figma стоит после выбора визуального направления, а не вместо него.

## Этапы отдельного чата

### 1. Дизайн-бриф

Зафиксировать аудитории, главные задачи ролей, характер продукта, желаемую деловитость, допустимую эмоциональность, брендовые материалы, ограничения доступности и производительности. Собрать 6–10 референсов: 2–3 по навигации и плотным таблицам, 2–3 по редакторам/конструкторам, 2–3 по визуальному характеру. Из каждого выписать применимый принцип, а не «сделать как этот сайт».

### 2. Три направления

Подготовить три компактных moodboard-направления на одном и том же тестовом экране: каталог курсов или Центр проверок. Для каждого: типографика, плотность, палитра, форма контейнеров, таблица, кнопки, иконки, состояния и один характерный приём. Выбрать одно направление и письменно зафиксировать причины.

### 3. Дизайн-система

Определить токены цвета, типографики, пространства, размеров, радиусов, границ, теней, слоёв, иконок и движения. Описать компоненты и состояния: navigation, table, filters, search, button, input, select/tree, dialog, drawer только где он оправдан, toast, inline error, empty/loading/skeleton, progress, status, tabs, breadcrumbs, DnD handle, editor toolbar, test question, review decision.

### 4. Ключевые экраны

Проработать минимум:

1. Каталог курсов.
2. «Описание / Программа / Предпросмотр» курса.
3. Редактор статьи Tiptap.
4. Конструктор теста.
5. Мастер назначения.
6. Центр проверок: обе рабочие вкладки.
7. Полноэкранную карточку сотрудника и просмотр попытки.
8. Пользовательское «Моё обучение» и прохождение курса на компьютере и телефоне.
9. Заглушки Базы знаний и «Требует действий».

Для каждого показать normal, loading, empty, error, disabled/denied, dirty/unsaved и conflict там, где они возможны.

### 5. Прототип и проверка

Собрать кликабельные пути: создание/редактирование курса, DnD программы, назначение кампании, прохождение теста, ручная проверка свободного ответа. Проверить иерархию, плотность, русские строки, 200% zoom, клавиатуру, focus, reduced motion, desktop 1440/1280/1024 и пользовательский экран 390 px.

### 6. Передача разработке

Передать:

- утверждённое направление и список запрещённых отклонений;
- токены в точных значениях;
- библиотеку компонентов и все состояния;
- макеты ключевых экранов;
- интерактивный прототип;
- правила адаптации и движения;
- реестр выбранных внешних компонентов с версиями и лицензиями;
- визуальные критерии приёмки и эталонные снимки;
- карту `макет → REQ/QA → маршрут приложения`.

## Текст для нового визуального чата

> Работаем только над визуальной системой RTM-Education-Next. Не меняй продуктовые правила и не начинай production-разработку. Сначала прочитай `AGENTS.md`, `docs/CURRENT_MVP_BASELINE.md`, `docs/VISUAL_DESIGN_WORKSTREAM.md`, затем профильные UX-контракты. Используй `development-workbench-skill` для процесса, `design-taste-frontend` для направлений, `ready-solutions-skill` для выбора компонентов, `no-ai-design-slop` как ограничения, `impeccable` для критики, `website-copy-typography` для русских текстов и `playwright` для проверки. Сначала подготовь бриф и три визуальных направления на одном экране. Не переносить решения в нормативную спецификацию до моего явного выбора. Итог — пакет дизайн-системы и макетов для передачи чату разработки.

## Критерий готовности визуального пакета

Разработка интерфейса начинается, когда выбран один визуальный тезис, определены токены и компоненты, проработаны перечисленные экраны и состояния, проверен прототип, а у команды есть точные эталонные снимки и критерии расхождения. Наличие красивого hero, набора карточек или общей палитры этим критериям не соответствует.
