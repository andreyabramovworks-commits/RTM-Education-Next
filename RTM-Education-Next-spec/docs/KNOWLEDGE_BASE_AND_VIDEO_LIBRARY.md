# База знаний: статьи, папки и материалы

**Статус:** утверждено 25.11.2026 для MVP. Прежние заглушки Базы знаний, отдельные каталоги документов/видео и Google Docs как самостоятельный пользовательский объект отменены.

Административная «База знаний» — одна кнопка и единое дерево вложенных папок. Администратор создаёт, именует, описывает и перемещает папки, выбирает обложку, создаёт статьи и перемещает статью между папками. Статья находится ровно в одной папке. Пользователь видит разрешённое дерево и читает статьи, не видит административных настроек.

Статья — отдельная сущность `articles`, содержащая упорядоченные блоки Tiptap: текст с форматированием, таблицы Tiptap и ссылки на материалы Google Docs, видео, аудио в произвольном количестве и порядке. Тест не вставляется в тело статьи. Статья может содержать плейлист из нескольких видео с описаниями. Встроенный Google Docs отображается как актуальное содержимое прямо на странице статьи RTM, а не как ссылка или внешняя вкладка. Собственный текст редактируется в Tiptap; текст Google Docs меняется только в Google. При недоступности Google явно показывать состояние ошибки. Нельзя выдавать старый кэш за актуальное содержимое.

`materials` содержит только `video`, `audio`, `test`, `google_document`; статьи туда не входят. У каждого типа своя таблица метаданных. Байты файлов вне PostgreSQL. Видео: ссылка на приватный/скрытый RUTUBE либо загрузка MP4, WebM, MOV на сервер. Аудио: загрузка MP3 или WAV на сервер. Встроенные плееры находятся в статье. Редактор загружает материал при создании статьи как из курса, так и из Базы знаний. Доставка серверных файлов проверяет право доступа и не отдаёт незащищённый постоянный URL.

Редакция принадлежит целой статье Базы знаний: тексту, порядку блоков и связанным материалам. При публикации редакции фиксируется компактный текстовый снимок содержимого встроенных Google Docs для исторического чтения и поиска. Обычное открытие статьи показывает актуальный Google Docs; просмотр исторической редакции показывает сохранённый снимок и явно обозначает его дату. Кампания «Обновления» назначает точную редакцию статьи. Публикация редакции сама не создаёт кампанию. В мастере редакции при режиме «Полный тест» создаётся отдельный тест после чтения статьи; он привязан к редакции. Для следующей редакции тест можно независимо скопировать с новым UUID, без попыток и результатов. Типы вопросов, попытки, проверка свободных ответов и награда соответствуют общему тестовому контракту.

Папочная База знаний реализуется через `knowledge_folders` (иерархия, название, описание, обложка), `knowledge_folder_articles` (размещение; уникальность по статье), `knowledge_access_grants` (цель folder/article, субъект department/subdepartment/employee). Разрешение папки открывает все текущие и будущие вложенные папки и статьи. Прямое разрешение статьи показывает цепочку её родительских папок и только эту статью. Правила только разрешающие, без запретов исключений. Backend проверяет листинг, поиск, открытие, историю редакций, встроенное видео/аудио и прямые ссылки. Структурные назначения отделу/подотделу применяются к актуальному составу сотрудников.

Первоначальное наполнение из существующей Google таблицы — однократный импорт Google Docs с последующей раскладкой статей по папкам. Дальнейшая иерархия поддерживается в RTM; постоянная синхронизация папок из таблицы не нужна.

Источник первого импорта — лист «Каталог документов» (gid `230795919`) таблицы `1NyZ3tC82_iWDsh3Y8UMtcpM5HXa6Ge13bBjI7UJ_7Xw`: название в B, описание в C, ссылки в G/H. Серые жирные строки создают корневые папки, синие жирные — вложенные, остальные жирные строки без ссылки — третий уровень папок. Строка с HTTPS-ссылкой создаёт статью в текущей папке; строка без ссылки, не являющаяся папкой, пропускается. Google Docs и Sheets вставляются в тело статьи как блоки с file ID; прочие HTTPS-ссылки сохраняются как ссылка на источник. Перед записью администратор видит количество новых записей и проблемные строки. Повторный запуск не создаёт дубли и не перезаписывает статьи, изменённые в RTM. Ссылки на документы, недоступные серверному Google-аккаунту, сохраняются, но сам документ не отображается до выдачи доступа.

## UX: создание и размещение

Админ открывает «База знаний» и видит дерево папок слева и таблицу статей текущей папки справа: название, описание, дата изменения, действующая редакция, права, действия. «Создать папку» просит название и необязательное описание/обложку; «Создать статью» открывает полный редактор Tiptap в выбранной папке. Перемещение статьи предлагает целевую папку и показывает, как изменится наследуемый доступ, перед подтверждением. Перемещение папки проверяет отсутствие циклов и также предварительно показывает изменение доступа. Поиск выдаёт лишь разрешённые результаты. Пустая папка, недоступный источник, неподдерживаемый файл, прерванная загрузка и конфликт редактирования имеют явные состояния и повтор.

В редакторе статьи команды «Текст», «Таблица», «Google Docs», «Видео», «Аудио» добавляют блок в позицию курсора. Для Google Docs выбирают зарегистрированный материал или подключают источник через админку БЗ; при выборе видны название, источник и статус доступа. Для видео выбирают RUTUBE URL или загрузку MP4/WebM/MOV, для аудио — MP3/WAV. В каждом блоке доступны перестановка, замена, удаление, описание и предпросмотр. Сохранение черновика и выпуск редакции — разные действия; предпросмотр не создаёт подтверждений. Запуск кампании обновления — третье отдельное действие.

## UX: доступ

Настройка доступа папки и статьи показывает получателей по отделам, подотделам и людям, а также итоговый эффективный доступ с пометкой «унаследован от папки» или «назначен статье». Сохранение ACL требует подтверждения, если доступ к уже видимым статьям меняется. Если назначен доступ только к статье, родительские папки отображаются как путь без ссылок на соседнее содержимое. Прямое открытие чужой статьи, сохранённой ссылки на файл или поиск по её названию получает одинаковый серверный отказ без утечки текста/метаданных.

## UX: редакция и обновление

Редактор открывает статью в «Управление редакциями», сравнивает текущий черновик с предыдущей редакцией, задаёт номер/дату/описание и выбирает режим подтверждения. «Полный тест» открывает конструктор общего тестового движка с возможностью создать тест заново или скопировать тест предыдущей редакции. Перед публикацией показываются состав блоков, статус Google Docs и возможность снять текстовый снимок; ошибка получения снимка блокирует публикацию редакции со встроенным Google Docs. После публикации отдельный мастер запускает кампанию с получателями, сроками и Bitrix. Сотрудник видит её в «Обучение → Обновления», читает зафиксированную редакцию статьи и выполняет выбранное подтверждение/тест. Старые снимки и попытки остаются неизменными.

Историческая редакция фиксирует порядок блоков, текст, ссылки на неизменяемые media asset IDs и текстовый снимок Google Docs. Замена файла создаёт новый asset ID для следующей редакции; прежняя продолжает воспроизводить прежний файл при сохранённом праве доступа.

В курсе отдельно создаётся внутренняя статья: она принадлежит курсу, не попадает в Базу знаний и не имеет пользовательских редакций. Google Docs в курсе вставляется как блок этой статьи через выбор зарегистрированного материала; отдельного элемента программы «Google Docs» нет. Копия статьи курса в другом курсе независима.

## Приёмочные сценарии

1. Администратор создаёт папку и статью, перемещает статью; она появляется ровно в одной папке.
2. Пользователь с доступом к одной статье видит цепочку папок, но не соседние статьи; прямой URL к соседней статье получает отказ backend.
3. Доступ к папке охватывает новые вложения без повторного назначения.
4. В одной статье перемежаются несколько видео, аудио, таблицы, текст и Google Docs; воспроизведение и чтение происходят внутри RTM.
5. Новая редакция сохраняет текстовый снимок Google Docs и назначается отдельно от публикации.
6. Тест редакции копируется в следующую редакцию с новым UUID и без истории попыток.
