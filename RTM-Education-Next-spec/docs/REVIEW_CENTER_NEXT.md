# Центр проверок — утверждённый интерфейс Next

**Ровно три вкладки.** Это договорённость пользователя 19.11.2026, заменяющая исторические четыре вкладки старого приложения. Принцип: раздельно контролировать **отдельно назначенные материалы** и **курсы**, без собственной четвёртой вкладки тестов и без редактирования контента в Центре.

## 1. Вкладка «Требует действий» — только заглушка в MVP

Показываем существующую вкладку и качественную плашку: «В будущих версиях здесь будет персональный список действий преподавателя: проверить назначенный тест/свободный ответ, напомнить о просроченном обучении, выдать дополнительные попытки, перейти прямо к нужному сотруднику или курсу». **Не реализуем настоящую сводную рабочую очередь в MVP.** Остальные две вкладки при этом сохраняют реальные действия преподавателя при открытии назначения.

## 2. Вкладка «Проверка отдельных материалов» — MVP полностью

**Назначение:** контролировать активные кампании обновлений статей Базы знаний и отдельно назначенных внутренних статей/тестов курса. Редакция принадлежит целой статье БЗ, в том числе со встроенными Google Docs, видео и аудио. Отдельной админ-вкладки «Материалы» нет. Статья или тест курса назначается отдельно через меню элемента и единый мастер.

**Показываем** материал лишь при наличии **активной кампании**. Первоначальная редакция без кампании не отображается. Выполнившие сотрудники продолжают присутствовать в статистике активной кампании. Несколько активных кампаний одного материала/редакции показываются **раздельно**, никакого случайного слияния.

### Вид «По материалам»

Иерархия `Цель назначения → активная кампания → сотрудники`; редакции есть у статей БЗ. Преподаватель видит любого сотрудника компании. Примеры целей: редакция статьи БЗ, отдельно назначенная статья либо тест курса. Основная строка кампании: название и тип цели, номер/дата редакции статьи при наличии, ID/название кампании, период запуска и дедлайн, назначения, выполнили N/%, в работе, ожидает проверки, просрочено, не приступили, ответственные, «Открыть»/«Все действия». При выборе кампании показывать участников, статус, срок, завершение, попытки, результат X/Y и награду за сданный тест.

### Вид «По сотрудникам»

**Одна строка — уникальный сотрудник** в выбранной активной выборке. Колонки: ФИО+аватар+должность, подразделение, назначено, выполнено, в работе/ожидает проверки, просрочено, процент, действие «Открыть». Карточка содержит **только** индивидуальные назначения отдельных материалов из активных кампаний (а не все элементы курсов поверх них). Возврат сохраняет группировку/фильтры/скролл.

### Фильтры

- Поиск по ФИО/статье/тесту/ID; тип статья БЗ/внутренняя статья/тест; подразделение с дочерними отделами; статус; дедлайн; способ подтверждения; ответственный. Фильтр редакции применяется к статьям БЗ.
- Сохраняются фильтры и сортировка при переходах. Различать `status` и `is_overdue`: можно быть одновременно «В процессе» и «Просрочено».
- Пересчитывать показатели по серверно отфильтрованному/доступному набору, показывать «Отображено X из Y» относительно всей разрешённой кампании. **Экспорт** — CSV или реальный XLSX по той же разрешённой сервером выборке, с UTF-8/BOM где нужно и корректными датами. Не сохранять TSV под расширением `.xls`.

### Статистика

Уникальные сотрудники; всего назначений; завершено N/%; не приступили; в работе; ожидают ручной проверки; возвращены; просрочены; освобождены отдельно. Процент выполнения = успешно завершённые / согласованный знаменатель (по умолчанию все учитываемые назначения), освобождённые **не выдаются за прошедших**. Суммы статусов и знаменатель не должны некорректно дублироваться при multi-department и повторных кампаниях.

### Карточка сотрудника — полноценная страница

**Не правый drawer.** Заголовок: «← Назад к списку», аватар/ФИО/должность/департамент, дата обновления, счётчики назначений/пройдено/просрочено. Ниже список назначений с целью, точной редакцией для статьи БЗ, ID кампании, способом прохождения, датами, статусом, просрочкой, ответственным, результатом и попытками теста, историей событий.

**Действия:** одна главная контекстная кнопка и **постоянное «Все действия»**, где доступны все разрешённые: напомнить, изменить срок конкретного назначения, выдать попытки конкретного теста, открыть все попытки/ответы, проверить свободный ответ, вручную подтвердить с обязательной причиной, освободить с обязательной причиной, открыть историю. При недоступности действия — причина. Права проверяет сервер. Все мутирующие операции — подтверждение и аудит.

## 3. Вкладка «Проверка курсов обучений» — MVP полностью

Аналогичный интерфейс и те же компоненты, но отдельная предметная область. В MVP показываются **активные кампании живых курсов** с постоянным `course_id`, техническими снимками совершённых действий и без рабочего списка завершённых кампаний.

### Вид «По курсам»

Иерархия `Курс → активная кампания → список участников → конкретный участник → программа/элементы/попытки`. Колонки: курс и дата изменения, период, участников, полностью завершили, средний прогресс, просрочено, ответственные, действие. Внутри курса показываем статистику, участников и индивидуальное прохождение.

### Вид «По сотрудникам»

Одна строка на уникального сотрудника с фото/ФИО/департаментом, число назначенных курсов, завершено, в процессе, просрочено, общий прогресс. В карточке — **только его курсы** из активных кампаний, без дублирования отдельных кампаний обновлений статей БЗ.

### Карточка сотрудника в курсе

Полноценный экран, не drawer. Breadcrumb `Курс → Сотрудник`. Дата изменения курса, начало/дедлайн, ответственные, статус, прогресс N из M required, процент. **Список элементов по разделам в актуальном порядке для незавершивших**: статья (внутри могут быть видео, аудио, Google Docs) или тест, текущий статус, дата подтверждения, предупреждение о просрочке. Тест можно раскрыть: все попытки, автоматический результат X/Y и решения free-text, право проверки и дополнительная попытка. При последовательном прохождении успешный тест разблокирует следующий required элемент по правилам. После возврата из теста или карточки сохранять местоположение.

### Фильтры и показатели курсов

Поиск курса/ФИО, подразделение с дочерними, статус, диапазоны прогресса 0/1–25/26–50/51–75/76–99/100%, дедлайн, преподаватель/«Мои курсы». Показатели: участники, назначения, завершили полностью N/%, средний прогресс по курсам, в процессе, просрочили, ждут проверки, освобождены (отдельно). *Процент завершивших* = завершившие / участники; *средний индивидуальный прогресс* = среднее индивидуальных долей; индивидуальный прогресс = завершённые обязательные элементы / все обязательные элементы ×100. При агрегировании нескольких курсов сотрудника учёт по сумме required-элементов предложен ранее и принят пунктами 1–7; требуется уточнить поведение «optional/освобождён». Не засчитывать pending review как completed.

## 4. Общее: активные и завершённые кампании

В обоих разделах заложить место для переключателя **«Активные / Завершённые»**, но **просмотр завершённых кампаний в MVP не реализовывать**, отображать «Появится в следующей версии». Активность кампании и индивидуальная успешность различны: сотрудник, уже прошедший активную кампанию, продолжает в ней отображаться. Кампания с 100% прохождением не скрывается автоматически до согласованного закрытия.

## 5. Одна система проверок тестов

**Нет отдельной вкладки «Проверка тестов».** Если тест назначен отдельно — его попытки открываются из «Проверки отдельных материалов». Если тест входит в курс — путь `Курс → сотрудник → тест → попытка`, в «Проверке курсов обучений». Обе точки входа ведут к одной backend-логике и одной странице review; обязательно передавать `assignment_id`, `course_item_id?`, `material_revision_id`, `attempt_id` и контекст возвращения. Все подробности в `TEST_REVIEW_WORKFLOWS.md`.

## 6. Защита от legacy-багов

Серверная пагинация и фильтрация; отмена устаревших запросов/контроль sequence number при переключении экранов; при refresh без сброса фильтров; один source of truth для назначений, не соединять устаревшие legacy массивы по совпадающим строкам; неизменные ключи React; оптимистичный UI без ложного результата; 403 на неразрешённые данные; дубликаты при sync/launch предотвращать уникальностью; реальные Playwright проверки переключений, крупных таблиц, истории/экспорта, конкурирующих оценок.

## 7. Критерии приёмки

RC01. Только три названные вкладки; «Требует действий» — честная заглушка.
RC02. Нет отдельного тест-review таба; тест из курса и standalone запускают **один** экран просмотра попыток.
RC03. При фильтре «Просрочено» completed не теряется из активной кампании, если фильтр не выбран; `overdue` остаётся отдельным признаком.
RC04. Открытая карточка — полноценная страница; возврат сохраняет состояние.
RC05. Курсы показывают прогресс required-элементов и не засчитывают pending_review.
RC06. Одна активная кампания материала/курса не смешивается со второй; неактивные без кампании не видны.
RC07. CSV и реальный XLSX соответствуют разрешённой выборке; чужие строки не выдаются.
RC08. Два последовательных запроса старой/новой фильтрации не вызывают гонку отрисовки.
RC09. Кнопка основного действия и «Все действия» доступны одновременно при наличии прав.
