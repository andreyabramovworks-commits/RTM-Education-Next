# Инструктаж для нового чата разработки

Работай с существующей папкой `RTM-Education-Next-spec`. Это единственная действующая спецификация. Не создавай параллельный набор документов и не начинай реализацию по одному пересказу из чата.

## Обязательное чтение до первого изменения

1. `AGENTS.md`.
2. `docs/CURRENT_MVP_BASELINE.md`.
3. `docs/DECISIONS.md`.
4. `docs/REQUIREMENTS_TRACEABILITY.md`.
5. `docs/MVP_CONTRACT.md`.
6. Профильные документы затронутой функции.
7. `docs/OPEN_QUESTIONS.md` и связанные строки `QUALITY_AND_TEST_MATRIX.md`.

После чтения кратко зафиксируй: затронутые REQ/ADR, владельцев UI/API/data/worker, открытые вопросы, проверки и пути, которые будут заменены. `SUPERSEDED` не реализовать. При расхождении с baseline сначала исправить документацию.

## Действующая модель, которую нельзя заменять старой

- Курс и внутренние статьи/тесты имеют постоянные UUID и живое содержание; пользовательских редакций у них нет.
- Кампании указывают на постоянный курс либо материал. История совершённых действий защищена техническими снимками.
- Только статьи Базы знаний имеют датированные пользовательские редакции; Google Docs отображается актуальным блоком статьи, исторический текст хранится в снимке редакции.
- Тест проходит по X/Y правильных автоматических ответов. Свободные ответы получают «Принято/Не принято». Баллы существуют только как награда за итоговое «Сдан».
- Преподаватель выполняет утверждённые действия для любого сотрудника компании, но не редактирует контент без роли редактора.
- Отдельной админ-вкладки «Материалы», «Видеотека» и четвёртой вкладки Центра проверок нет.

## Порядок реализации вертикального среза

1. Проверить реальные файлы проекта, стек и установленные зависимости.
2. Выбрать один пользовательский сценарий из спецификации.
3. Реализовать необходимую часть data → domain/transaction → API/RBAC → UI/states → worker/integration.
4. Не создавать временный параллельный бизнес-путь, если уже существует владелец поведения.
5. Проверить нормальный, denied, invalid и failure сценарии, конкурентность и идемпотентность там, где они относятся к функции.
6. Обновить REQ/ADR/QA и документацию, если реализация выявила необходимое уточнение. Не принимать продуктовые решения молча.
7. Запустить `python scripts/validate_spec.py` и применимые проверки кода.

## Ограничения выпуска

Не изменять `/opt/rtm-app` и production-код. Не выполнять commit, push, tag, release и deployment без отдельного явного разрешения пользователя. После разрешённого push в `main` должен использоваться отдельный автодеплой Next; до его фактической установки нельзя сообщать, что он уже работает.

## Отдельный визуальный поток

Если визуальный пакет ещё не утверждён, использовать `VISUAL_DESIGN_WORKSTREAM.md` как план отдельного дизайн-чата. Не придумывать окончательную палитру и стили в ходе случайной реализации одного экрана. Утверждённые токены, компоненты, макеты и эталонные снимки затем включаются в рабочий контракт интерфейса.

## Результат каждого этапа

Сообщить: что изменено, какие REQ/ADR выполнены, какие проверки реально запущены, какие состояния просмотрены в браузере, какие вопросы остаются открыты. Успешная сборка не заменяет проверку поведения; структурный валидатор не заменяет профильные тесты.
