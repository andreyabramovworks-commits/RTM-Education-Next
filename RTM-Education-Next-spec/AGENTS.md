# AGENTS — RTM-Education-Next (утверждённые правила + требования ведения спецификации)

> Этот файл адаптирован из `references/AGENTS.original.md`. Оригинал сохранён побайтово без изменений. Старые факты о текущем автодеплое `/opt/rtm-app` — **только исторический контекст**; Next ещё предстоит изолированно настроить. Конкретные названия доступных локальных навыков из оригинала применяются лишь там, где они действительно установлены и доступны.

1. **Исходный код правим только в локальном репозитории**, после проверки действующего пути. Не наслаиваем параллельные реализации поверх работающих; при замене переносим вызовы, удаляем устаревшее, проверяем регрессии.
2. До публикации локально запускаем применимые тесты, линтеры, сборку и Docker Compose; сообщаем результаты и границы проверки.
3. **Никаких `commit`, `push`, tag, release без отдельного явного разрешения пользователя на публикацию.** Документацию в черновых файлах можно готовить без коммита; отправка в GitHub только по отдельной команде.
4. Публикация: уникальный тег `vX.Y.Z`, ключ `RTM-YYYYMMDD-NN`, понятное сообщение коммита, проверка незанятости тега и его связи с коммитом; затем push коммита и тега по правилам выпуска.
5. **Next автоматически обновляется из `origin/main` после разрешённого push** после того, как независимый deploy-service будет установлен и проверен. Не утверждать, что он уже существует. Автодеплой включает миграции Alembic, сборку и проверку состояния; не подменять теговую политику выдуманным деплоем из GitHub Release.
6. После деплоя проверить фактическую версию, health/readiness, контейнеры, миграции, логи и затронутые сценарии. Не считать успешный push успешным deploy.
7. **На production запрещено редактировать исходный код.** SSH разрешён для диагностики и эксплуатационных операций в пределах разрешения. Не коммитить `.env`, токены, пароли, ключи SSH, приватные данные сотрудников, дампы и файлы резервных копий.
8. Все изменения структуры PostgreSQL — только через Alembic-миграции. Никакой правки production-БД в обход согласованного процесса.
9. Интеграции Bitrix24 и Google — через backend; секреты не уходят в браузер. Доступ к сотрудникам/проверкам контролируется сервером.
10. Сохранять изоляцию Next от работающего предшественника `/opt/rtm-app`: отдельные каталоги, Docker project, БД, volumes, конфигурация и адреса после согласования.
11. Для одноразовой dev-БД не внедрять автоматические бэкапы; **до появления реальных данных сотрудников** настроить проверяемые резервные копии PostgreSQL и медиа. GitHub восстанавливает код/миграции, но не строки БД.
12. Иерархия ролей: **разработчик > администратор > редактор > преподаватель > пользователь**. Администраторы Bitrix24 получают admin в RTM; developer защищён. Преподаватель не редактирует контент. Редактор имеет админку, но не раздаёт роли. Полномочия по конкретным сотрудникам/кампаниям требуют серверной проверки.
13. Перед реализацией сверяться с `docs/DECISIONS.md` и `docs/REQUIREMENTS_TRACEABILITY.md`: отменённые решения не копировать в код. При изменении требования обновлять его ID, статус, связанные контракты и проверки **в этом же наборе файлов**; записать причину/источник и конфликт в `docs/CHANGELOG.md`.
14. Отличать `APPROVED`, `PROPOSED`, `OPEN`, `SUPERSEDED`. Нельзя представлять предложенную UI-раскладку или неразрешённую бизнес-логику как принятую.
15. После правки документации выполнить `python scripts/validate_spec.py`: проверить наличие файлов, все трассировочные ID и ссылки, отсутствие старого утверждения о самостоятельной вкладке «Материалы» или четырёх вкладках Центра проверок в нормативном тексте. Старые факты могут находиться только в разделе «отменено/исторический контекст».
16. Перед проектированием, реализацией или ревью обязательно прочитать `docs/CURRENT_MVP_BASELINE.md`, затем `docs/DECISIONS.md`, `docs/REQUIREMENTS_TRACEABILITY.md`, относящиеся к задаче профильные документы, `docs/OPEN_QUESTIONS.md` и связанные проверки. Реализовывать только действующую спецификацию; при противоречии сначала согласовать и исправить документы.

## Навыки (если доступны локально)

Из оригинала: `development-workbench-skill` — основной процесс; `kodmaster` — углублённая диагностика; `ready-solutions-skill` — проверка лицензий и готовых компонентов; `impeccable` и `web-creator` — UI, `playwright` — реальный браузер. Не имитировать выполнение отсутствующих навыков. Их подробные правила читать из оригинального файла и локальной установки, когда они реально доступны.
